I reviewed `latent-workflow-ontology-RESULTS.md` Turn 9 against the uploaded source tree from `wrkq-060726113656.zip`. This is a static source review, not a live adapter/runtime exercise.

Two framing corrections matter before the individual gap calls:

First, the assessment’s preamble overstates wrkf↔wrkq state coupling. wrkf does **not** project canonical workflow state into `tasks.state`; it writes workflow state into `tasks.meta.workflow` only (`internal/workflow/service.go:584-619`). The task document hash explicitly treats `task.State` as separate data and removes `meta.workflow` before hashing (`internal/workflow/service.go:447-459`). So “wrkq task state is a same-transaction projection of wrkf state” should be refuted.

Second, the “hash-chained append-only event ledger” claim is overclaimed. The schema has `prev_event_hash` and `event_hash` columns (`internal/db/migrations/000014_wrkf_schema.sql:38-63`), but inserts compute `eventHash := Hash(payloadJSON)` and do not populate `prev_event_hash` (`internal/workflow/service.go:560-569`, `internal/workflow/ledger.go:1605-1617`). So there is an event log with per-event payload hashes, but not a source-enforced hash chain.

## Gap assessment

**G-01 — effect “delivered” ≠ confirmed. Accept; severity MED-HIGH.**  
The source validates this. `Effect` stores status, attempts, lease fields, and `deliveredAt`, but no persisted receipt, external confirmation, or resulting-object reference (`internal/workflow/types.go:267-282`; schema at `000014_wrkf_schema.sql:152-167`). The RPC type even has `Receipt` on `EffectAckParams`, but `EffectAck` ignores it and calls `AckEffect(effectID, leaseToken)` only (`internal/wrkfapi/types.go:92-96`, `internal/wrkfapi/effect.go:24-32`). `DeliverEffect` can return JSON stdout as a transient receipt, but successful exit just calls `AckEffect`; the receipt is not stored (`internal/workflow/ledger.go:1122-1138`). Lease-token ack is better than fire-and-forget, so I would not call this critical across all effect kinds, but for handoff/dispatch/task-creation effects the gap is real.

**G-02 — checks gate on presence, not substance. Partially accept; original wording is too broad; severity MED.**  
The current source is stronger than the assessment: it has `facts_json` on workflow evidence (`000019_workflow_evidence_facts.sql:3-8`), `KindSpec.Facts`, `EvidenceRequirementSpec.Facts`, `Predicate.EvidenceExists.Facts`, and `FactEquals` in the model (`internal/workflow/types.go:38-55`, `85-88`, `141-152`). Facts contracts are validated at template install and evidence add time (`internal/workflow/facts.go:42-67`, `176-232`), and fact selectors are actually matched during transition blocking (`internal/workflow/facts.go:366-410`; `internal/workflow/service.go:1438-1479`). The PBC template uses typed facts for key routing, for example `pressure_pass.verdict` and `patch_decision.route` (`pbc/workflow-template.json:88-123`, `354-365`, `475-489`).  

The residual gap is that these facts are still self-asserted scalar summaries, while `data_json` is only checked for JSON validity (`internal/workflow/service.go:790-798`). Presence-only requirements still exist for kinds like `behavior_note`, `pbc_draft`, and `pbc_final` (`pbc/workflow-template.json:200-204`, `367-368`, `490+` region). So: refute “presence only” as a blanket claim; accept “shape/small-fact validation is not semantic artifact verification.” MED is right generally; MED-HIGH only for transitions whose safety depends on unverified external artifact content.

**G-03 — SoD asserted but under-declared and actor-id-shallow. Accept; severity should be upgraded to MED-HIGH.**  
The assessment is directionally correct, but its schema detail is stale: current `RoleSpec` has only `Description`, not candidate actors/capabilities/bind fields (`internal/workflow/types.go:34-36`). There is a `workflow_role_bindings` table (`000014_wrkf_schema.sql:65-74`), but transition enforcement only checks a caller-supplied role string. Worse, `roleAllowed("", by)` returns true (`internal/workflow/service.go:1030-1040`), and CLI role defaults to empty unless `--role` or `WRKF_ROLE` is supplied (`internal/wrkfcli/root.go:122-130`). Transition passes that role directly (`internal/wrkfcli/root.go:685-689`), and the kernel denies only when `roleAllowed` returns false (`internal/workflow/ledger.go:1348-1350`). There is no declarative “producer actor must differ from verifier actor/session/model” rule. In trusted single-user local mode this is medium; in multi-agent or adversarial agentic workflows it is high enough to upgrade.

**G-04 — obligations have no obligee and no waiver authority. Accept; severity MED-HIGH.**  
The source validates this cleanly. Obligation creation has only `kind`, `ownerRole`, `ownerActor`, `blocking`, and `reason` (`internal/workflow/types.go:129-135`), and persisted obligations have owner/status/satisfied evidence but no obligee, waiver actor, waiver authority, or discharge policy (`internal/workflow/types.go:252-265`; `000014_wrkf_schema.sql:138-150`). `SetObligationStatus` accepts `satisfied`, `waived`, or `cancelled` without actor/role input and updates by obligation id + instance only (`internal/workflow/ledger.go:713-752`). That means a blocking obligation is a strong interlock structurally, but waiver is not authority-checked. MED-HIGH is validated; it becomes HIGH when obligations are used as safety or review gates.

**G-05 — verdicts do not go stale when their artifact changes. Accept; severity MED-HIGH.**  
The source has partial dirtiness tracking for the task document, not for arbitrary evidence artifacts. `Evidence` stores `ref`, `facts`, `data`, `source`, actor/role/run info, `taskEtagAtProduction`, and `producedAt`, but not a produced-from content hash or supersession edge (`internal/workflow/types.go:225-239`; `000014_wrkf_schema.sql:117-130`). `AddEvidence` records `source_json` as an external ref and task etag, but does not hash or dereference the external artifact (`internal/workflow/service.go:809-821`). Check runs do have `input_hash` (`internal/workflow/types.go:290-307`; schema `000014_wrkf_schema.sql:97-115`), but transition reuse loads the latest check by `(instance, transition, check)` and does not compare the stored input hash to the current context (`internal/workflow/service.go:1481-1511`; transition reuse at `internal/workflow/ledger.go:1376-1389`). There is a parallel wrkq `evidence_items.content_hash` surface (`internal/db/migrations/000013_task_workflow_schema.sql:55-78`), but wrkf workflow evidence does not use it. The severity is valid.

**G-06 — no task↔task dependency edge; no program/aggregate completion. Refute as written; accept narrower wrkf-integration gap; severity MED.**  
The broad “no task↔task dependency edge” claim is false in the source. wrkq has `task_relations` with `blocks`, `relates_to`, and `duplicates` (`internal/db/migrations/000002_planning_layer.sql:262-290`), domain constants for those kinds (`internal/domain/types.go:59-66`), blocker queries (`internal/store/tasks.go:1024-1063`), inverse queries (`internal/store/tasks.go:1065-1085`), and docs defining `Task A blocks Task B` (`docs/DOMAIN-MODEL.md:300-318`).  

The narrower gap is real: wrkf transitions do not automatically consult `task_relations`, and there is no first-class wrkf program/rollup instance. There are some hard-coded delegated-task/coordinator/observer obligations created from specific evidence kinds (`internal/workflow/service.go:825-837`), but that is not a general cross-task dependency ontology. So split the finding: task dependency edge is present; wrkf dependency semantics and aggregate completion remain under-modeled. Original HIGH should be downgraded to MED for wrkf integration, LOW-MED for aggregate/program completion as a larger feature.

**G-07 — no declarative per-outcome postcondition. Accept narrowly; severity LOW-MED.**  
`OutcomeCase` has `when`, `to`, `effects`, and `obligations`, but no `postcondition` or equivalent declarative assertion (`internal/workflow/types.go:113-120`). Template validation only checks that the target state is declared and that outcome metadata is structurally valid (`internal/workflow/service.go:188-205`). The assessment’s claim that “beforeCommit hook” is the fallback is stale for current source: `TransitionSpec.Hooks` and `StateHooks` exist as fields (`internal/workflow/types.go:28`, `57-68`), but transition runtime does not execute named lifecycle hooks; actual hook execution is for check hooks and effect handlers (`internal/workflow/service.go:1634-1642`; `internal/workflow/ledger.go:1070-1081`). This is a mild rigor gap because the engine itself sets `outcome.to`; it matters more for external artifact/effect invariants than for state assignment.

**G-08 — legality-surface soundness for `next`. Accept, but refute “cannot adjudicate statically”; severity MED for framework, LOW for current PBC preset.**  
Static source review can adjudicate at least one unsoundness. `Next` considers current state, caller role, evidence/obligation blockers, and check blockers, then emits a transition action using `tr.Outcomes[0].To` as the expected state (`internal/workflow/service.go:1252-1299`). It does **not** evaluate `tr.Guards` or route outcome predicates. Actual `Transition` does evaluate guards and then selects the first matching outcome, rejecting when none match (`internal/workflow/ledger.go:1394-1408`). Therefore a template using guards or routed outcomes can produce a `next` action that the engine later rejects, or advertise the wrong expected state. The current `pbc/workflow-template.json` appears to avoid guards and multi-outcome transitions, so impact on that preset is low, but for the engine contract this should be upgraded from LOW/unknown to MED.

**G-09 — effects have no ordering guarantee; idempotency is narrow. Partially accept; severity LOW-MED to MED.**  
There is no explicit per-instance effect sequence field in `Effect` or `workflow_effects` (`internal/workflow/types.go:267-282`; `000014_wrkf_schema.sql:152-167`). Claims and lists use `ORDER BY created_at, id` (`internal/workflow/ledger.go:804-814`, `877-978`), so “no ordering at all” is too strong; there is FIFO-ish selection. But that is not a causal ordering contract, and concurrent/batched adapters can still make external delivery order differ.  

Idempotency is stronger than the assessment implies for transition retries: transition idempotency stores request hash and result JSON and replays the exact committed result for the same idempotency key (`000020_transition_idempotency_result.sql:1-4`; `internal/workflow/ledger.go:1321-1329`, `1565-1589`). However, effect keys include instance, revision, outcome, and newly allocated effect id (`internal/workflow/ledger.go:1481-1499`), so distinct transitions/re-emissions can still create semantically duplicate effects with distinct keys. MED is valid for non-commutative effects; otherwise LOW-MED.

**G-10 — template/catalog afterlife undefined. Partially accept; severity MED for hook/effect-heavy workflows, LOW for hookless presets.**  
The template half is refuted. Installed templates persist `definition_json` and hash in `workflow_templates` (`000014_wrkf_schema.sql:3-10`), install rejects same id/version with a different hash (`internal/workflow/service.go:266-292`), and `ShowTemplate` loads the persisted definition from DB (`internal/workflow/service.go:317-330`). Moving the original template file should not brick an installed instance.  

The catalog half is real. Hook catalogs are discovered from filesystem/env paths (`internal/workflow/service.go:1773-1867`), not pinned by content to template or instance. Hook checks fail if catalog or hook id is unavailable (`internal/workflow/service.go:1634-1641`), and effect delivery fails if no handler is registered (`internal/workflow/ledger.go:1070-1081`). So: refute “template afterlife undefined,” accept “hook/effect handler catalog afterlife undefined.”

## Overreach assessment

**C-01 — six-phase hook machinery is heavy. Refute for current source; severity NONE/LOW.**  
The source does not implement the claimed six-phase lifecycle (`beforeTransition`, `validate`, `beforeCommit`, `afterCommit`, `onReject`, `onError`). The data model has generic `StateHooks` and transition `Hooks` fields (`internal/workflow/types.go:28`, `57-68`), but runtime hook execution is limited to check hooks and effect handlers. The PBC template has no checks and no hook catalog dependency. This may be a spec/documentation overreach, but not a current implementation cost.

**C-02 — “assurance theater.” Partially accept; severity MED-HIGH, but rename the failure mode.**  
The phrase is too dismissive because the source has real assurance machinery: typed facts, transition CAS via revision/context hash, idempotency replay, effect leases, and blocking obligations. But the root-of-trust critique is valid: role is caller-supplied and empty role bypasses role gating; actor identity is a string; facts are self-asserted; waiver is ungoverned; SoD is absent. I would call this an **assurance boundary mismatch**, not pure theater. Severity is MED-HIGH because the system pays real ceremony for guarantees that stop short at identity, authority, and semantic evidence truth.

**C-03 — hard template immutability + one-active-instance is rigid. Accept; severity MED for iterative agentic work, LOW-MED generally.**  
Templates are immutable by `(id, version)` hash: re-installing the same id/version with different content errors (`internal/workflow/service.go:274-280`). Instances enforce one non-closed workflow per task (`000014_wrkf_schema.sql:34-36`). This is a deliberate consistency tradeoff, not a bug. It simplifies auditability and state authority but makes mid-task workflow evolution/forking/migration a new-version problem. MED is fair when agents are expected to refine the workflow while work is ongoing.

**C-04 — deterministic next-action ranking assumes too much determinism. Mostly refute/downgrade; severity LOW.**  
`Next` emits deterministic ranks and sorts descending (`internal/workflow/service.go:1297-1301`), and `NextAction` carries `Rank`, `Mode`, `Confidence`, and `Command` (`internal/workflow/types.go:381-395`). But `NextActionModel` is only a field and appears unused in runtime code, and the docs explicitly warn that `NextAction.Command` is human guidance, not authority (`docs/WRKF_RPC.md:382-386`). The bigger problem is not over-investment in ranking precision; it is G-08’s incomplete legality mirroring. LOW severity is validated.

**C-05 — beware deontic creep when fixing obligations. Accept as prospective caution; severity LOW-MED.**  
Current source is under-modeled, not over-modeled: obligations lack obligee, waiver authority, and actor-aware discharge. But the caution is correct: the fix should probably be minimal—add obligee/beneficiary and no-self-waiver/waiver-authority checks—rather than a full deontic/Hohfeldian logic engine. LOW-MED is appropriate because this is a future-design risk, not a current implementation overreach.

## Restated for a highly technical engineer

G-01 means `workflow_effects.status='delivered'` is an adapter-level ACK, not a durable proof that the external system changed state. Treat it like an outbox row marked done after a worker says “I did it,” without a persisted receipt or read-after-write confirmation. The lease protocol is useful, but the state name overstates the guarantee.

G-02 means the engine now validates more than row existence—`facts_json` is real—but it still mostly validates a compact, self-reported decision surface. The kernel can require `{verdict:"ready"}` or `{route:"finalize"}`, but it does not prove the underlying artifact actually supports that fact unless a hook or external verifier does so. The gap is not “there are no facts”; it is “facts are not evidence provenance.”

G-03 is an authorization/modeling hole. Transitions are gated by role strings, but role membership and separation-of-duty are not first-class constraints. In the CLI path, an empty role bypasses `by` entirely. That makes `by:["reviewer"]` more like a convention than a robust capability check.

G-04 is an obligation-discharge authority bug. A blocking obligation is a good primitive, but waiver is just a status update, not an operation checked against an authority model. Without obligee/waiver-authority, the same actor responsible for satisfying the debt can clear the debt.

G-05 is missing build-system-style invalidation. Checks record an `input_hash`, and evidence records task etag, but transitions do not reject reused check verdicts when the check’s input context/artifact has changed. The system needs a dependency edge from verdict → artifact hash or verdict → evidence version, then stale-on-change semantics.

G-06 should be split. wrkq already has a task dependency graph via `task_relations(kind='blocks')`. The missing piece is that wrkf does not consume that graph as part of workflow legality, and there is no aggregate workflow/program instance that computes “done” from child task closure.

G-07 is a design-by-contract gap. Outcomes have preconditions and a target state, but no declarative postcondition saying “after this outcome, property P must be true.” The engine can mechanically set state, but it cannot assert richer post-state invariants except by ad hoc checks/hooks.

G-08 is a source-visible `next` conformance bug. `wrkf next` approximates transition legality but does not evaluate all the predicates the real transition path evaluates. For templates with guards or routed outcomes, the advisory surface can diverge from the authoritative engine.

G-09 is an outbox semantics gap. Effects are selected in timestamp/id order and transition retries are idempotent for the same key, but there is no explicit causal sequence or semantic dedupe key for effects. If handlers are non-commutative or duplicate-sensitive, the contract needs either stronger sequencing/idempotency or a clear “handlers must tolerate reorder/duplicate” rule.

G-10 is not really about installed templates; those are persisted in DB. It is about external executable dependencies. Hook catalogs and effect handlers are runtime filesystem artifacts, not content-pinned dependencies of the workflow instance, so a live instance can become unable to check or deliver after catalog drift.

C-01 is not a current implementation overreach. The six-phase lifecycle described in the assessment is not implemented in the source path being reviewed.

C-02 is best understood as a trust-boundary mismatch. The engine has nontrivial structural safeguards, but the parts that decide who is allowed to act and whether evidence is true are still too soft for high-assurance agentic work.

C-03 is a deliberate rigidity tradeoff. Immutable templates and one active instance per task make audit/replay sane, but they make workflow evolution behave like schema migration: safe, explicit, and somewhat heavy.

C-04 is a minor concern. `next` ranks actions deterministically, but the implementation is not deeply invested in probabilistic planning machinery. The real engineering issue is legality conformance, not ranking philosophy.

C-05 is a good guardrail for future fixes. Add the smallest authority model that closes self-waiver and directed obligation gaps; do not turn obligations into a full legal logic subsystem unless a real preset requires it.
