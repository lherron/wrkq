T-05362 wrkf scheduler ASPC/HRC manifests Daedalus approved

Named contracts and agent manifests, not scanner loops.

The proposal makes wrkf the durable authority for discovering, claiming, fencing, and recovering workflow work while ASPC/HRC answer which agents may be assigned and agent-loop executes the selected handler.

Lance explicitly rejected scheduler-owned hash/provenance machinery. The final design uses named handler contracts, handler versions, ASPC-compiled agent work manifests, HRC agent matching, lease/fence safety, and mandatory implement-to-verify continuation.

01 / final review

Daedalus approved the simplified boundary.

The current proposal keeps the scheduler mechanics and removes scheduler-owned hash/provenance tracking. Daedalus found no blocking edits and approved the ASPC/HRC/wrkf/agent-loop split.

approved

Production requires durable wrkf authority

Runner-only work remains a non-production vertical spike. Unattended scheduling needs wrkf claims, leases, fences, release, and reaper behavior.

rejected

No scheduler-owned provenance layer

No manifest hashes, prompt-bundle hashes, schema hashes, capability hashes, source provenance, or delivery-ref provenance for scheduler admission.

precision

wrkf must not call HRC inside claim transactions

The runner calls HRC first. claimNext validates the supplied HRC/ASPC tuple against current wrkf state under CAS before leasing.

02 / operating model

The runner asks HRC who can work, then wrkf what is legal.

The design rejects task scraping, generic "do the next thing" prompts, and local workflow memory. Assignment comes from ASPC/HRC; execution legality comes from wrkf.

03 / contract plane

Execution is selected by named contracts and explicit assignability.

Workflow templates declare what kind of work is needed. ASP owns handler and prompt source. ASPC compiles what each agent may do. HRC answers who can do this action now. wrkf records the selected contract and assignee.

template

Action slot

Names the semantic action, role, handler contract, output evidence, side effects, and continuation policy.

ASP

Handler manifest

Publishes handler contract, handler id/version, schema refs, side-effect classes, and implementation reference.

ASPC

Agent work manifest

Compiles explicit declarations for roles, handler contracts, work classes, project scopes, workspace modes, and exclusions.

HRC

agentManifest.match

Lists assignable agents for the proposed task/action without requiring agent-loop to parse ASP source files.

wrkf

Claim admission

Validates the caller-supplied HRC/ASPC tuple against current workflow state and imported handler facts before leasing.

explicit no

No provenance burden

Scheduler admission does not require prompt, schema, manifest, capability, source, or delivery provenance fields.

06 / continuation policy

TDD, implementation, and e2e stay one attention unit.

The ledger still records separate actions. The scheduler treats them as an exclusive-attention group when verification is mandatory.

After implement.done, the same instance and exact source implement action/commit are pinned until verify terminalizes or becomes operator_required.
happy path

Claim continuation directly

The same runner can move from implement to verify through claimContinuation after re-querying the instance.

crash path

Recover from ledger discovery

A restarted runner finds implemented-but-unverified work from instance/action-run truth, independent of live claim rows.

no fallback

Never use latest implement

Verify bindings carry the exact source implement action run and source commit.

operator state

Infrastructure failure does not free the worktree

If verify cannot launch operationally, the scheduler keeps the pin, expires into recovery, or reports operator_required.

07 / dynamic worksets

Cross-repo lanes are discovered facts, not up-front decomposition.

A simple task can start as ordinary implementation work. If impact discovery proves multiple repos are needed, the workflow stores a typed workset as evidence and the scheduler materializes lane-scoped candidates from that ledger fact.

08 / staged plan

The first slice proves shape; the second builds authority.

The phase names matter because the durable scheduler core is still not production-ready until handler contracts, agent manifests, continuation policy, and verify-launch authority are settled.

phase 1

Non-production vertical spike

  • Use existing wrkf.instance.next and wrkf.action.*.
  • Run packaged triage, implement, and verify handlers.
  • Prove one-runner continuation only.
  • No crash-safety or multi-runner guarantee.
phase 2

Durable scheduler core

  • Settle effect-lease reuse versus scheduler-claim table.
  • Add discover, claim, heartbeat, release, and reap.
  • Add ASP handler publish, ASPC manifest compile, and HRC list/match.
  • Add fence semantics and action-run start/resume replay.
phase 3

Continuation hardening

  • Encode continuation policy in templates or wrkf policy catalog.
  • Recover implement -> verify across restarts.
  • Resolve scheduler verify versus ACP verify-launch authority.
  • Define dynamic workset evidence and lane materialization.
phase 4

Intake cleanup

  • Decide automatic wrkq-simple-task@1 attachment.
  • Retire standalone scanner loops except compatibility cases.
  • Route normal executable work through scheduler discovery.
09 / visible checks

Acceptance is about recovery and refusal, not throughput.

The most important tests prove stale actors cannot write, verified work cannot be skipped, and terminal work is not repeated.

must fail closed

Safety checks

  • Two schedulers cannot claim the same workflow instance.
  • Stale fences cannot complete, fail, transition, release, launch, or mutate worktrees.
  • claimNext refuses unsupported or unassignable capabilities inside the transaction.
  • ACP verify-launch and scheduler continuation cannot double-launch verify.
must recover

Recovery checks

  • Terminal action plus expired claim reconciles without re-running the action.
  • Runner crash after implement still discovers verify before fresh work.
  • Verify carries exact sourceImplementActionRunId and source commit.
  • Cross-repo worksets materialize from typed evidence, not agent memory.
  • Active orphaned actions can be reclaimed or failed without hiding the task forever.
