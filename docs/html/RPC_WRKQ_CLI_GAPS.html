Summary RPC Catalog Command Matrix Critical Gaps DTO Gap Migration Order
2026-06-22 / wrkq

wrkq can start migrating to RPC, but byte parity needs new protocol surface.

The existing JSON-RPC interface covers the core resource model. The current CLI also exposes projections, streams, search/index operations, handoffs, webhooks, local process controls, and legacy output contracts that are not represented in RPC today.

Core covered Tasks, comments, attachments, relations, containers, legacy actors, and workflow attachment have basic RPC methods.
Parity blocked `cat`, `set`, `ls`, `find`, `rm`, `mv`, and `restore` have behavior or fields beyond the current DTOs.
Missing areas Search/index, monitor/watch/log, handoffs, webhooks, copy, diff, bundle, and rich tree projections need decisions.

Three Migration Lanes

The audit separates commands that can use RPC soon from commands that need DTO widening or entirely new RPC namespaces.

Use soon

Resource primitives

Basic task, comment, attachment, relation, and container operations have matching RPC methods. These are good candidates for the first mirror implementation.

Widen first

CLI projections

Commands such as `cat`, `ls`, `find`, `stat`, and `tree` depend on aggregate or legacy shapes that current resource DTOs do not provide.

Add or keep local

Operational surfaces

Search/index, monitor/watch/log, handoff, webhook, bundle, agent, and server commands need new namespaces or explicit local-only decisions.

What RPC Has Today

The current method catalog is strong for resource CRUD and workflow operations. It does not expose most CLI-specific projections.

Command Gap Matrix

The most important rows are marked partial: a method exists, but the current CLI cannot be byte-compared against it without added fields, projections, or adapter behavior.

`touch`, `set`, `cat`

Partial

Task create/show/update exist, but `set` lacks several fields, `touch` lacks force UUID and project-linkage fields, and `cat` emits a richer task document with comments, relations, blockers, artifact_dir, and async run fields.

`ls`, `find`, `tree`, `stat`, `projects`

Projection gap

RPC has separate task/container list and show calls. The CLI returns mixed task/container projections, rollups, compact metadata, hierarchy, project-root exceptions, and legacy snake_case output.

`rm`, `mv`, `restore`, `mkdir`, `rmdir`

Semantic gap

Container create/delete and task move/delete/restore exist, but CLI behavior includes archive vs delete semantics, rename, multi-source operations, confirmation, dry-run, recursive deletion, and restore-with-move/comment updates.

`comment *`, `attach *`, `relation *`

Mostly covered

Core operations are present. Gaps remain for comment purge/dry-run/CAS/multi-ref, attachment stdin and file-byte retrieval, richer list/show output, and exact presentation parity.

`search`, `index *`

Missing

No `wrkq.search.*` or `wrkq.index.*` methods exist. These commands operate the local sidecar index, freshness checks, ranking, snippets, and background index state.

`log`, `watch`, `monitor *`

Missing

No wrkq event-log or monitor namespace exists. `wrkf.event.query` is workflow-event scoped and does not replace CLI event history, raw watch, or terminal monitor contracts.

`handoff *`, `webhook *`

Missing

Handoffs and global/per-container webhook mutations have no RPC methods today. Container webhook changes also need a container update method.

`cp`, `apply`, `diff`, `bundle create`

Missing or partial

`apply` can end in task.update after local parsing, but has no RPC apply method. Copy, diff, and bundle export are not represented in RPC.

`agent`, `agent-context`, `server *`, `usage`, `version`, `whoami`

Likely local

These are process, runtime, environment, documentation, or local identity surfaces. Keep them local unless a control-plane RPC is deliberately introduced.

Critical Cutover Blockers

These are the issues that will break a byte-comparison harness if the mirror CLI simply swaps command handlers for current RPC calls.

Delete semantics do not match

CLI `rm` defaults to archive behavior. RPC `wrkq.task.delete` sets `state=deleted` and `deleted_at`. That cannot be substituted silently.

Task detail is narrower than `cat`

`WrkqTask` lacks current CLI fields such as artifact_dir, project_id, parent display fields, blocker summary, comments, relations, resolution, and async run linkage.

Streams are absent

`log`, `watch`, and `monitor` depend on event_log reads, polling, condition evaluation, and terminal NDJSON records. There is no equivalent RPC namespace.

Presentation contracts are separate work

RPC uses camelCase resource DTOs. CLI machine output often uses snake_case, table rows, raw markdown, porcelain IDs, and command-specific aggregate summaries.

Task Patch Contract Gap

The fastest way to unblock core command migration is to widen task update semantics before routing `set` through RPC.

Current `TaskPatch`

interface TaskPatch {
  title?: string;                  // display title
  description?: string;            // task body
  specification?: string;          // task spec body
  state?: WrkqTaskState;           // lifecycle state
  priority?: number;               // 1..4
  kind?: string;                   // task kind
  riskClass?: string;              // risk class
  labels?: string[];               // label set
  meta?: Record<string, unknown>;  // metadata object
  assigneePrincipalRef?: string;   // assignee
  dueAt?: string | null;           // due date
  startAt?: string | null;         // start date
}

Needed for `wrkq set`

interface CliParityTaskPatch extends TaskPatch {
  slug?: string;                   // task path segment
  parentTask?: string | null;      // parent or clear parent
  requestedByProjectId?: string;   // return-to project
  assignedProjectId?: string;      // owning project
  resolution?: string;             // done / wont_do / duplicate
  cpProjectId?: string;            // external CP project
  cpWorkItemId?: string;           // external work item
  cpRunId?: string;                // external run
  sessionId?: string;              // stored as cp_session_id
  runStatus?: string;              // queued / running / terminal
}

Recommended RPC Work Order

The migration should avoid command-by-command cutover until a mirrored Cobra tree and comparison harness can prove behavior.

1

Mirror first

Add the parallel RPC-backed Cobra tree and command-tree parity test before changing production `wrkq` behavior.

2

Start with low-projection reads

Implement basic relation, attachment list/remove, comment show/list, and container show paths where current RPC is closest.

3

Widen task mutations

Extend task patch/create/delete/restore semantics before attempting `touch`, `set`, `rm`, `restore`, or `cat` parity.

4

Add projection namespaces

Add or deliberately compose rich projections for `cat`, `ls`, `find`, `tree`, `stat`, and `projects`.

5

Decide operational scope

Choose which command groups become RPC-backed and which stay local: server, agent, usage, version, search/index, monitor, handoff, webhook, bundle.
