Refined wrkf structured evidence proposal

Facts route. Data explains.

Add structured evidence to wrkf by splitting each evidence record into a rich freeform payload for humans and agents, plus a small validated facts object for workflow decisions.

Core model

Keep evidence useful without making workflows own artifact schemas.

The proposal adds one new evidence column and one template-level contract surface. The engine gets just enough structure to route, while evidence producers keep their full artifact body freeform.

Current gap

Evidence is currently presence-only.

The existing wrkf model already has facts for check runs, but evidence itself only carries a kind, reference, summary, data, and source. Transition requirements and predicates can ask whether a kind exists, not what decision it made.

KindSpec

Only description exists

`KindSpec` carries `Description` and no kind-specific decision contract.

RequirementSpec

Requires by kind only

`requires.evidence.kind` can express "pressure_pass exists" but not "pressure_pass verdict is ready".

EvidencePredicate

Predicates mirror the limit

`evidenceExists` checks a kind and cannot branch on structured evidence decisions.

Design implication The proposal extends the current evidence seam instead of replacing it: old templates remain valid, old evidence remains readable, and presence-only requirements keep their behavior.

Add `workflow_evidence.facts_json` as nullable JSON. App-level validation remains the source of truth; the database check, when available, is corruption resistance.

Template contract

Facts contracts belong to the installed template.

There is no global schema registry and no external schema file. The installed workflow template version carries the evidence kind facts contract, so routing semantics are versioned with the workflow that uses them.

Template shape

Named structs before extension

Replace anonymous requirement structs with named `EvidenceRequirementSpec` and `ObligationRequirementSpec`, then extend evidence requirements and predicates with raw JSON facts.

  • `EvidenceRequirementSpec.Facts map[string]json.RawMessage`
  • `EvidencePredicate.Facts map[string]json.RawMessage`
  • `KindSpec.Class` and `KindSpec.Facts`
required

Field names that must be present when an evidence kind has a contract.

properties

Declared validation for known facts, keyed by fact name.

type

`string`, `boolean`, `number`, `integer`, or `array`.

enum

Raw JSON values matched with exact JSON semantics.

bounds

`maxLength`, `maxItems`, and scalar-only `itemsType` for arrays.

{
  "pressure_pass": {
    "class": "review",
    "facts": {
      "required": ["verdict"],
      "properties": {
        "verdict": {
          "type": "string",
          "enum": ["ready", "needs_patch", "too_vague"]
        }
      }
    }
  }
}
Contract discipline

Malformed templates fail early.

Template validation rejects invalid types, dangling `required` entries, enum/type mismatches, invalid `itemsType`, negative bounds, and malformed facts predicates. Misspelled fields must not become silent no-ops.

Facts validation

Flat, permissive where safe, strict where declared.

`AddEvidence` parses and validates facts after loading the latest workflow instance and installed template. Unknown additional fields are allowed when flat; known fields must satisfy their declared contract.

Known kind, no facts contract

No facts or a valid flat facts object is accepted.

accept
Known kind, required facts

Missing required fields, invalid enum, wrong type, or bad bounds are rejected.

reject
Unknown kind

Preserve current behavior: accept no facts or valid flat facts.

accept
Any kind, nested object facts

Nested objects are out of scope. Arrays are allowed only with scalar values.

reject
Any kind, non-object facts

`[]`, strings, numbers, booleans, and malformed JSON are rejected for `facts`.

reject
Numbers

UseNumber or raw JSON

Tests must make `1`, `1.0`, integer rejection, and enum comparison behavior explicit.

Bias

Prefer strings and booleans

Routing facts should avoid unnecessary numeric ambiguity.

Data payload

Still just valid JSON

`data_json` remains a rich artifact payload and is not validated by facts contracts.

Matching semantics

The newest decision of a kind wins.

One shared matcher should serve transition blockers, `evidenceExists` predicates, suggestions, next-action generation, and blocked-transition reporting. This avoids drift between command surfaces.

01
Find latest by kind Order by `produced_at`, then `id`; historical matches do not override the latest decision.
02
No facts condition means presence-only Existing requirements continue to pass when evidence of the kind exists.
03
Facts condition requires exact keys All requested facts must JSON-equal the latest evidence facts.
04
Mismatches block with detail Messages distinguish missing evidence, no facts, and latest fact mismatch.

required evidence pressure_pass with facts verdict=ready is blocked;
latest verdict=needs_patch from ev_000014

required evidence pressure_pass with facts verdict=ready is blocked;
latest evidence ev_000014 has no facts

API and CLI

Evidence creation needs named params and `--facts`.

As evidence creation grows, the service call should move away from positional strings. Both manual evidence creation and command-executed evidence must accept facts, or required-facts evidence kinds become unusable from `evidence exec`.

Context hash

Decision facts are now workflow context.

Presence-only hashing by `kind:ref` was acceptable before facts controlled routing. Once facts decide transitions, context hashing should include evidence ID, kind, ref, and a facts hash.

Before

`kind:ref` only

A new `pressure_pass` with a different verdict can change routing without enough context protection.

refs = append(refs, e.Kind+":"+e.Ref)
After

`id:kind:ref:Hash(facts)`

The hash distinguishes repeated decisions and protects transitions from stale evidence facts.

refs = append(refs,
  e.ID+":"+e.Kind+":"+e.Ref+":"+Hash(e.Facts))
Preferred behavior Adding evidence should update `workflow_instances.context_hash`, `workflow_instances.updated_at`, and any task meta workflow projection needed for consistent routing.

PBC workflow example

Branching becomes explicit without parsing prose.

The PBC preset can express clarification and pressure-pass decisions as facts, while preserving full analysis and review payloads in evidence data.

Analysis

`clarification_needed=true`

`ask_clarification` passes only when the latest pre-interview analysis asks for clarification.

Analysis

`clarification_needed=false`

`draft_pbc` passes only when the latest analysis says no clarification is needed.

Review

`verdict=ready`

`finalize_ready_pbc` passes only when the latest pressure pass is ready.

Review

`verdict=needs_patch`

`request_patch_decision` passes only when the latest pressure pass asks for a patch.

Implementation order

Land the storage seam before routing behavior.

The proposal is additive, but the blast radius is broad because every evidence reader must carry facts consistently. The safest path is storage, types, validation, API, matcher, behavior, then presets.

Storage and typesAdd migration, update `workflow.Evidence`, and propagate facts through all scanners, loaders, outputs, snapshots, hooks, effects, obligations, and context construction.
Template modelName requirement structs, add `KindSpec.Class`, `KindSpec.Facts`, `FactsContract`, and `FactProperty`.
ValidationValidate template facts contracts, parse facts with stable number handling, and enforce flat object rules inside `AddEvidence`.
Creation surfacesReplace positional `AddEvidence`, add `--facts` to `evidence add` and `evidence exec`, and return facts in command output.
Routing surfacesCentralize latest-evidence matching and use it in transition blockers, predicates, suggestions, `next`, and blocked messages.
Context and presetRefresh context hash on evidence add, update snapshot/export/import behavior, and move PBC to `pbc-progressive-refinement@3`.

Test matrix

The key regressions are compatibility, latest wins, and stale context.

Tests should cover old templates, old evidence, validation edges, raw JSON matching, CLI parity, suggestion detail, next-action blockers, and PBC smoke behavior.

Compatibility

Old templates, old evidence, presence-only requirements, and unknown kinds keep working.

Validation

Reject non-object facts, nested objects, invalid enums, missing required facts, and invalid bounds.

Numeric

Document and test `1`, `1.0`, integer rejection, and numeric enum comparison.

Template

Reject invalid property types, dangling required entries, invalid itemsType, and bad predicates.

Matching

Older ready plus newer needs_patch blocks ready; newer ready passes ready.

CLI

`evidence add --facts` and `evidence exec --facts` store and return facts.

Suggestions

Report missing kind, latest mismatch, required facts, latest facts, and satisfaction state.

Context

Adding evidence facts changes context hash and stale `--context` rejects transitions.

Recommendation Adopt structured evidence facts as an additive wrkf primitive. The two critical refinements are raw JSON comparison through one matcher, and treating evidence facts as workflow context.
